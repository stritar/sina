ゲートが問題を見つけても、常に扉を閉ざすわけではありません。各違反は、次に何が
起きるかを決める**重大度**を持ちます。3 つあります。

<EnforcementLadder />

- **`flag`** は情報提供です。決定に記録され、コンプライアンスやレポートに役立ちますが、
  何も阻止しません。5,000 ドルの送金はレビュー対象として記録され、それでも通過します。
- **`escalate`** は標準のレンダリングを阻止し、**代わりにより厳格なコンポーネントを強制
  します**。上限を超える電信送金は、2 人目の承認者を求める `SecureWireDialog` へ
  エスカレーションします。リクエストは拒否されるのではなく、より安全な経路へ振り向けられます。
- **`reject`** は完全な阻止です。何もマウントされません。捏造されたボタン、密輸された
  カードデータ、または自己承認された送金は、単に拒否されます。

<Callout variant="note" title="1 つの決定は複数を伴い得る">
  1 つのインテントは、同時に複数の違反を引き起こし得ます。承認されていない 60,000 ドルの
  電信送金は 2 回フラグが立ち（報告対象、レビュー）、*さらに* 1 回エスカレーションします。
  フラグは記録され、ダイアログを強制するのはエスカレーションです。
</Callout>

<Callout variant="tip" title="正直な注記">
  重大度は各規則のロジックの性質であり、グローバルなオン/オフのスイッチではありません。
  強制を「緩める」には、規則、またはどのインテントをゲートに通すかを変更します。それは
  コードの中で、意図的に、レビュー可能な形で行われます。
</Callout>

## クリーンに通過したとき何がマウントされるか

通過した表示動詞は、その表示用コンポーネントをマウントします。クリーンに通過した
**統制された**動詞は何もマウントしません。決定は `mount: null` とともに返り、
アプリは `core` プリミティブから組み立てた独自の確認ステップを用意します。SINA は
何が許可されるかを決め、ホストがハッピーパスを所有します。

```ts
{ intent: "wire_transfer", props, result: { valid: true /* … */ }, mount: null }
```

統制されたコンポーネントは、エスカレーションが強制したときにだけマウントされます。

アプリ全体を初日から統制する必要はありません。規則は独立しているため、単一のインテントから
始めて、そこから広げていけます。[段階的に導入する](/docs/guides/adopt-incrementally)を
参照してください。
