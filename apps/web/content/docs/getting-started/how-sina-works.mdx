SINA has one moving part, and it's easy to picture. There are three actors:

1. **The model proposes.** The AI sends an *intent* — a verb plus some data, like
   "wire_transfer" with an amount and a recipient. It never names a component.
2. **The server decides.** Your server runs the intent through the **Constitution**
   — a set of rules written as schemas. The rules answer one question: is this
   allowed, and if so, what should render?
3. **The screen shows what passed.** SINA mounts the component the server chose.
   If the request failed, nothing unsafe renders.

## Walk it once: a wire transfer

Say your banking assistant wants to move money. Here's the same flow twice.

**A $500 transfer.** The intent has a valid amount, currency, and recipient. It's
below every regulatory limit. The gate passes it, and SINA mounts an accessible
summary of the transfer. Done.

**A $60,000 transfer.** Same shape, bigger number. The gate checks it against the
rules and finds three things: it's reportable, it's flagged for review, and — the
one that matters — it's **over the $50,000 secondary-approval limit**. So the
gate refuses to mount a plain confirm button. Instead it forces a
`SecureWireDialog` that requires a *second person* to approve. The AI cannot skip
this. There is no code path that renders an un-approved transfer.

<Callout variant="enforced" title="Why it can't be bypassed">
  The check runs on your **server**, before anything reaches the browser. The AI
  only ever sends data; the server alone picks the component. So even a hostile
  AI can't force the unsafe version — it was never allowed to choose.
</Callout>

That's the whole model. Everything else in SINA — accounts, cards, disclosures,
read-only data — is this same three-step flow with different rules.

## Three layers, one flow

Under the hood, SINA is three layers stacked on each other. You mostly think about
the flow above; the layers are just how it's packaged.
