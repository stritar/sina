title: How SINA works
---

Every AI-generated screen in SINA goes through the same three steps:

1. **The model proposes.** The AI sends an <Term term="intent">intent</Term>: a
   verb plus some data, like `"wire_transfer"` with an amount and a recipient.
   It never names a component.
2. **The server decides.** Your server runs the intent through the
   <Term term="constitution">Constitution</Term>, your rules written as schemas.
   They answer one question: is this allowed, and if so, what should render?
3. **The screen shows what passed.** SINA mounts the component the server chose.
   If the request failed, nothing unsafe renders.

## The one rule everything rests on

> **The model sends an intent and props, never a component. Validation runs on
> the server only. We validate, _then_ mount. We never mount, then check.**

Why your server, and not the browser? Because **once UI reaches the screen, you
can't take it back.** React streams it down piece by piece. There is no
"un-render."

So the check has to run **before anything mounts**. The last place you fully
control is your own **server**. An attacker can edit or skip whatever runs in
the browser. A check there stops honest mistakes; **it does not stop an attack**.

That's the payoff. It doesn't matter whether the model is wrong, jailbroken, or
hostile: **it never decides what renders.**

## What an intent looks like

```ts
const intent = {
  intent: "wire_transfer",
  props: { amount: 6000000, currency: "USD", recipient: /* … */ },
};
```

Notice what's *not* there: no button, no dialog, no layout. The AI describes
*what* it wants ("move this money"), never *how* it should look.

## What the gate checks

Every intent goes through the same four steps, in order:

1. **Structure.** Is the payload exactly the right shape? Schemas are strict, so
   a fabricated "Confirm" button or a smuggled card number is an *extra field*,
   rejected before any value is read.
2. **Policy.** Do the values obey the rules? Is the amount within limits? Is a
   second approver required? Every threshold is cited to a real standard.
3. **Decision.** Problems become *violations*, and the gate decides: valid or
   not, and if a stricter component is required, which one.
4. **Audit.** Every decision emits a record of what was asked, what was decided,
   and which rules fired, with sensitive data redacted first.

A decision always ends one of two ways: **it mounts** (the request passed, SINA
mounts the component the rules chose), or **it's blocked** (the unsafe version
never mounts; it is refused outright, or
<Term term="escalation">escalated</Term> to a stricter component like a
second-approver dialog).

<Callout variant="note" title="The gate names a component">
  The gate doesn't return "allowed / denied." It names *one specific* component,
  as `requiredComponent: "SecureWireDialog"`, or it refuses. That component, and
  nothing else, is what mounts. A design system, not just a policy engine.
</Callout>

## Three layers, one flow

Under the hood SINA is three layers: tokens and primitives, the governance seam,
and the domain constitution. You mostly think about the flow above. The layers
are just how it's packaged.
