章程的规则会解析为两种 UI。**受治理的组件**渲染一次升级，即规则强制施加的更严格
流程。**展示模式**渲染一次干净的读取。二者本身都不做任何校验；每一个都只是渲染
关卡已经做出的决定（[工作原理](/docs/how-it-works)）。

## 三个受治理的组件

数十条受治理的规则最终只升级到**三个**组件。规则各不相同；而安全的目的地是共享的，
且久经考验。

- **`SecureWireDialog`**：当一笔电汇需要第二位审批人时被强制。它运行双人复核循环：
  审阅确切条款 → 收集一位*不同*审批人的身份 → 用一次性验证码确认 → 在服务器上重新
  校验。一次被拒的重新校验会让对话框保持打开，因此无法"点击绕过"。参见
  [6 万美元电汇](/docs/governance/wire-transfer)。
- **`GovernedActionDialog`**：当几乎任何其他需要授权的操作升级时被强制：ACH、P2P、
  账单支付、外汇（FX）、卡操作、额度变更、开户、交易。与电汇对话框形状相同，条款则
  由该操作派生。SINA 正是这样覆盖整个银行应用，而无需为每个流程定制对话框。
- **`MandatoryDisclosure`**：当用户必须确认必读文本时被强制：保证金适当性、贷款
  （TILA）披露、外汇点差告知。文本来自规则而非模型，因此 AI 无法软化、缩短或跳过
  法律要求的告知。

<Callout variant="note" title="每次都是相同的阶段">
  三者共享一个状态机：审阅 → 收集 → 待处理 → 已解决。只需学习一种交互模式，测试一组
  状态，在每个受治理的流程中都获得一致的无障碍体验。
</Callout>

## 展示模式

真实的应用大部分时间都在*展示*内容。展示规则没有限额或审批，但它仍会检查**形状**
（严格解析）、**边界**（列表有上限）和**隐私**（标识符必须被掩码）。三者全部通过，
SINA 就挂载一个展示型组件：`TransactionList`、`BalanceCard`、`PortfolioHoldings`
及其同类，约两打，每种读取对应一个。

两个属性完成安全工作。模型选择*展示什么*，但**由你的服务器提供数值**，因此它无法凭空
捏造余额。而且读取是**只读的**：任何展示组件都不会渲染裸露的操作按钮。从列表中执行
操作（对某笔扣款提出争议、支付账单）是一个新的意图，会重新进入关卡。

## 意图注册表

模型从 `fintechIntentManifest()` 中选取一个**动词**；注册表将它映射到对应的规则和
组件。模型从不指名某个组件。

| 意图 | 类型 | 挂载 / 升级到 |
|---|---|---|
| `wire_transfer` | 受治理 | `SecureWireDialog` |
| `ach_transfer` · `p2p_payment` · `bill_pay` · `fx_convert` · `withdraw` | 受治理 | `GovernedActionDialog` |
| `add_payee` · `link_account` · `kyc` · `change_limit` · `issue_card` · `card_control` · `security_change` | 受治理 | `GovernedActionDialog` |
| `place_trade` · `enable_margin` · `credit_request` | 受治理 | `GovernedActionDialog` · `MandatoryDisclosure` |
| `disclosure` | 受治理 | `MandatoryDisclosure` |
| `list_transactions` | 展示 | `TransactionList` |
| `account_balance` | 展示 | `BalanceCard` |
| `portfolio_holdings` | 展示 | `PortfolioHoldings` |
| `spending_breakdown` · `budget_progress` · `list_cards` · `list_payees` · … | 展示 | 展示型读取 |

<Callout variant="note" title="未知动词一律拒绝">
  不在注册表中的意图会被拒绝为 `UNKNOWN_INTENT`，并且仍会被审计。默认是拒绝，而非
  放行。
</Callout>

## `@sina-design-system/fintech` 目录

这些 schema 位于 `@sina-design-system/fintech`：纯 Zod，无 React，无 UI。单一入口点
为一切路由：

```ts
import { evaluateFintechIntent } from "@sina-design-system/fintech";

const { valid, violations, requiredComponent } = evaluateFintechIntent({
  intent: "wire_transfer",
  props: { amount: 6000000 /* $60,000 in minor units */ },
});
```

| 分组 | 内容 |
|---|---|
| 受治理的 schema | `wire-transfer`, `ach-transfer`, `p2p-payment`, `bill-pay`, `fx-convert`, `add-payee`, `kyc`, `issue-card`, `card-control`, `change-limit`, `place-trade`, `credit-request`, … |
| 展示类 schema | `transaction-list`, `account-balance`, `portfolio-holdings`, `spending-breakdown`, … |
| 格式基础组件 | `currency` (ISO 4217)、`amount`（整数最小货币单位）、`iban` (ISO 13616)、`bic` (ISO 9362)、`routing` (ABA)、`card` (Luhn)、`masked-account`、`step-up` |
| 引用的阈值 | `thresholds.ts`：每个数值限额都是带引用出处的具名常量 |
| Fixtures | 每个 schema 都在 `fixtures.ts` 中附带有效载荷与对抗性载荷 |

权威目录是 `packages/fintech/PATTERNS.md`。要向其中添加：
[编写一条治理规则](/docs/governance/writing-a-rule)。
