这是 SINA 的旗舰流程，也是文档其余部分所指向的规范化演练。我们将跟随一笔 60,000
美元的电汇，从请求到解决。其他每一个受治理的流程都是这个流程的变体。

## 请求

AI 提议一笔转账。它只发送数据：一个意图和 props，绝不发送组件（参见[工作原理](/docs/how-it-works)）。

```ts
{ intent: "wire_transfer",
  props: { amount: 6000000 /* $60,000 in cents */, currency: "USD", /* … */ } }
```

## 结构检查

首先是严格解析。每个字段都会对照 schema 进行检查：金额是以最小单位表示的整数，货币代码真实有效，账户标识符通过其校验和。任何
schema 不认识的字段，例如夹带的 `confirmButton` 或多余的 `cvv`，都会拒绝整个负载。这个请求格式正确，因此继续往下走。

## 策略检查发现三件事

形状有效，因此策略开始运行。它触发了**三项**违规，每一项都会引用其来源：

| 发现 | 严重程度 | 标准 |
|---|---|---|
| 应申报交易（CTR） | `flag` | FinCEN, 31 CFR 1010.311 |
| 可疑活动审查（SAR） | `flag` | FinCEN, 31 CFR Ch. X |
| 超过 50,000 美元的审批上限 | `escalate` | SINA 双重控制策略 |

这两个 flag 是信息性的：会被记录，但不会阻断。**escalate** 才是采取行动的那一个。它拒绝普通的确认，并指定
`requiredComponent: "SecureWireDialog"`。（严重程度在[升级](/docs/concepts/escalation)中有介绍。）这里也会触发一次审计事件，携带时间戳、负载、全部三项违规以及决定的组件。在任何内容渲染之前，阻断就已经记录在案。

## 强制对话框

SINA 会挂载 `SecureWireDialog`，而不是一个确认按钮。该对话框引导第二个人完成：

1. 在只读摘要中**审查**确切条款（金额、收款人）。
2. **表明身份**为审批人，其 ID 和姓名必须与发起人不同。
3. 使用一次性代码**确认**。

当他们提交时，证据会**返回服务器**，章程会再次运行。对话框本身不校验任何内容。它只负责收集审批。

<Callout variant="enforced" title="两项检查让它无法被绕过">
  在第二次通过时，服务器强制执行两件恶意流无法伪造的事情。**双人复核（四眼原则）**：审批人必须与服务器已知的发起人不同，因此你无法审批自己的电汇。**负载绑定**：审批与确切条款绑定，并在服务器上重新计算，因此你无法审批
  5,000 美元却执行 60,000 美元。
</Callout>

在下面的演示中，发起人尝试审批自己的电汇。四眼原则直接拒绝，并且从那里无法继续。

## 圆满结局

治理会升级，而不只是拒绝。一个*有效*的审批会在第二次通过时通过关卡：一位不同的经理，绑定到确切的
60,000 美元条款。随后转账会作为一个已完成的、受治理的操作被挂载。第二次[审计事件](/docs/concepts/audit-trail)记录谁批准了、基于什么条款，以及关卡已通过。整个过程之后仍可重建：阻断、审批、通过。

试试看。打开强制对话框，以*不同*的经理身份审批，服务器会重新检查，决定随之翻转。以发起人身份审批，它会拒绝。

<Recap>
超限电汇 → 严格解析通过 → 三项违规（两个 flag，一个 escalate） → `SecureWireDialog` →
一位*不同*的审批人 + 一次性代码 → 服务器重新检查四眼原则和负载绑定 →
批准并挂载，或被拒绝，每个决定都附带一次审计事件。普通确认从来都不是一个选项。
</Recap>
