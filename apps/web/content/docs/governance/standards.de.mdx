SINAs goldene Regel lautet: **niemals ein Limit erfinden**. Jeder Schwellenwert, jedes
Format und jedes Pflichtfeld lässt sich auf einen Standard oder eine Aufsichtsbehörde
zurückführen, mit der Quellenangabe im Code. Diese Seite ist der Beleg: jeder Standard, den
die Verfassung kodiert, und für jeden *was der Code tatsächlich prüft*.

Diese letzte Spalte ist der springende Punkt. Eine Liste von Standards ist eine
Compliance-Behauptung, und Compliance-Behauptungen sind genau der Punkt, an dem ein
Governance-System anfängt, Sie anzulügen. Deshalb nennt jede Zeile den **Mechanismus**,
nicht den Anspruch: SINA berechnet die mod-97-Prüfsumme einer IBAN tatsächlich, aber es
prüft keine Adresse gegen eine Sanktionsliste und führt keine PCI-Bewertung durch. Wo eine
Regel nur ein dünner Ersatz für eine tiefgreifende Pflicht ist, sagt die Zeile das.

Regeln fallen in drei Stufen, und der Code hält sie auseinander:

- **Format**: Prüfsummen und Codelisten. Deterministisch, eine Nutzlast erfüllt sie also
  oder nicht.
- **Regulatorisch**: echte Vorschriften. Ein `flag` hält den Befund im
  [Audit-Trail](/docs/concepts/audit-trail) fest; ein `escalate` erzwingt eine geregelte
  Komponente; ein `reject` verweigert rundheraus. Nicht dazu gedacht, leichtfertig gelockert
  zu werden.
- **SINA-Richtlinie**: einstellbare Produktvorgaben (Vier-Augen-Prinzip, Step-up-Limits).
  **Kein Gesetz.** Das sind die, die Sie an Ihre eigene Risikobereitschaft anpassen sollen.

Wenn der Kontrollpunkt eine Anfrage blockiert, reist der `standard` aus der passenden Zeile
mit dem Verstoß in den Audit-Datensatz. Eine Blockade ist nie ein Rätsel, und ein Prüfer
kann sie bis zu der Zeile zurückverfolgen, die sie ausgelöst hat. Siehe
[den Vertrag](/docs/concepts/the-contract) für die Form und
[eine Regel schreiben](/docs/governance/writing-a-rule), um eine hinzuzufügen.

<Callout variant="enforced" title="Diese Tabelle wird aus den Schemas generiert">
  Der Katalog lebt im Verfassungspaket, nicht auf dieser Seite, und ein Guard-Test bindet
  beide aneinander: eine Regel, die einen Standard zitiert, den der Katalog auslässt, lässt
  den Build fehlschlagen, und ebenso ein Katalogeintrag, der etwas zitiert, das keine Regel
  durchsetzt. Die Dokumentation kann nicht vom Code abweichen und keine Prüfung behaupten,
  die es nicht gibt.
</Callout>

## Was das Gate durchsetzt, und wo es aufhört

SINA ist ein Gate zur Renderzeit und wirkt daher auf fünf Weisen auf eine Anfrage: Es
validiert Struktur und Format, es eskaliert oder markiert beim Überschreiten eines
Schwellenwerts, es erzwingt die Bestätigung einer Offenlegung, es verlangt eine
zusätzliche Verifizierung (Step-up) oder einen zweiten Genehmiger, und es schwärzt den
Audit-Trail. Jede Zeile unten ist einer dieser fünf Schritte.

Drei Arten von Kontrolle liegen bewusst außerhalb dieser Reichweite. SINA gleicht keinen
Namen und keine Adresse gegen eine Live-Sanktions- oder PEP-Liste ab, es trifft keine
Kredit- oder Berechtigungsentscheidung im Backend, und es besitzt keine
Geldtransmitter-Lizenz. Jede davon braucht einen Dienst und Live-Daten, die ein UI-Gate nie
sieht. SINA läuft **vor** ihnen, es ersetzt sie nicht, und eine Zeile, die sich auf eine
davon stützt, sagt das.

Die ehrliche Form der Abdeckung ist also diese. Die Geldbewegungsschienen und die
Meldeschwellen sind hier: Travel Rule, SAR, CTR, Vier-Augen-Kontrolle, PCI-Feldhygiene.
Sanktionsabgleich, Entscheidungen zu fairer Kreditvergabe und Lizenzen bleiben außerhalb
des Rahmens und werden ausdrücklich so ausgewiesen, niemals als grüner Haken vorgetäuscht.
Einige Gate-förmige Regeln sind schlicht noch nicht gebaut, etwa die starke
Kundenauthentifizierung für EU-Abläufe und die Einwilligung zum Datenzugriff im Open
Banking. Um eine hinzuzufügen, siehe
[eine Regel schreiben](/docs/governance/writing-a-rule).

<Callout variant="note" title="Außerhalb des Rahmens ist ein Feature, kein Loch">
  Ein Governance-System gewinnt Vertrauen, indem es seine Grenzen benennt. SINA steht vor
  Ihrem Abgleich und Ihrer Backend-Entscheidung, daher ist es sicher, die Grenze klar zu
  benennen, statt eine Prüfung anzudeuten, die der Code nie ausführt.
</Callout>
