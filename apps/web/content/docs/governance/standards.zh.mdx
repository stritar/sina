SINA 的黄金法则是**绝不臆造限额**：每一个阈值、格式和必填字段都能追溯到某个标准或某个监管机构，
并在代码中附带引用。本页就是凭据：章程编码的每一项标准，以及针对每一项，*代码实际检查了什么*。

最后那一列才是重点。一份标准清单本身就是一种合规声明，而合规声明恰恰是治理系统开始欺骗你的地方。
因此每一行说明的是**机制**，而非愿景：SINA 会真正计算 IBAN 的 mod-97 校验和，但它不会将地址与制裁
名单进行比对，也不会执行 PCI 评估。当某条规则只是对某项深层义务的单薄替代时，该行会如实说明。

规则分为三个层级，代码将它们区分开来：

- **格式**：校验和与代码列表。具有确定性，因此一个载荷要么满足要么不满足。
- **监管**：真实的法规。`flag` 会将该发现记录到[审计追踪](/docs/concepts/audit-trail)中；`escalate`
  会强制使用受治理的组件；`reject` 则直接拒绝。不可随意放宽。
- **SINA 策略**：可调的产品默认值（双人复核、升级限额）。**并非法律。** 这些正是你应当根据自身风险
  偏好来调整的项。

当关卡拦截一个请求时，匹配行中的 `standard` 会随违规一起进入审计记录。拦截绝不是谜团，审计员可以将
其追溯到产生它的那一行。关于其形态，参见[契约](/docs/concepts/the-contract)；要新增一条规则，参见
[编写规则](/docs/governance/writing-a-rule)。

<Callout variant="enforced" title="此表由这些 schema 生成">
  目录存放在章程包中，而非本页，并且有一个守卫测试将二者绑定：一条规则若引用了目录中缺失的标准，会
  导致构建失败；同样，目录中的某一条目若引用了没有任何规则强制执行的内容，也会导致构建失败。文档无法
  偏离代码，也无法声称一项并不存在的检查。
</Callout>

## 关卡强制执行什么，以及到哪里为止

SINA 是一个渲染时关卡，因此它以五种方式作用于一个请求：校验结构与格式、在超过阈值时升级或标记、强制确认一份披露、要求进行额外验证（step-up）或第二位审批人，以及对审计追踪进行脱敏。下面的每一行都是这五种动作之一。

有三类控制被有意排除在这一范围之外。SINA 不会将姓名或地址与实时制裁名单或 PEP 名单进行核对，不会在后端做出放贷或资格决定，也不持有货币传输牌照。它们每一个都需要一个 UI 关卡永远看不到的服务和实时数据。SINA 运行在它们**之前**，并不取代它们；凡是依赖其中之一的行，都会如实说明。

所以覆盖范围诚实的样子是这样的。资金流转通道与申报阈值都在这里：Travel Rule、SAR、CTR、双人控制、PCI 字段卫生。制裁核对、公平放贷决定和牌照均在范围之外，并且被明确声明为如此，绝不伪装成一个绿色的通过标记。一些具有关卡形态的规则只是尚未构建，例如面向欧盟流程的强客户认证，以及开放银行的数据访问同意。若要添加一条，请参阅[编写规则](/docs/governance/writing-a-rule)。

<Callout variant="note" title="超出范围是一项特性，而非漏洞">
  治理系统通过明确说出自己的边界来赢得信任。SINA 位于你的核对与后端决策之前，因此稳妥的做法是把边界讲清楚，而不是暗示一个代码从不执行的检查。
</Callout>
