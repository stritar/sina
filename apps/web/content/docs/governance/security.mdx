---

SINA assumes the AI producing intents might be wrong, jailbroken, or actively
hostile. So the design question is never "will the model behave?" — it's "what
happens when it doesn't?" Here's every attack we defend against, and why each
fails.

## The attacks, and the defenses

| The attack | What it tries | Why it fails |
|---|---|---|
| **Fabricated control** | Smuggle a `confirmButton` into the payload | Strict schema — unknown fields are rejected before any value is read |
| **Smuggled card data** | Include a `cvv` or full PAN | Same strict parse; and redaction drops/masks it so it never hits a log |
| **Over-limit action** | A $60,000 wire with no approval | Policy escalates it to a second-approver dialog; the raw confirm can't mount |
| **Self-approval** | Approve your own transfer | Four-eyes check — approver must differ from the server-known initiator |
| **Bait-and-switch** | Approve $5,000, then execute $60,000 | Approval is bound to the exact terms; the server recomputes the binding hash |
| **Fabricated data** | Invent an account balance or transaction | For reads, the server supplies the values — the model only picks *what* to show |
| **Data exfiltration** | Return an unmasked account number | Display schemas require masked identifiers; a full number is rejected |
| **Flooding** | Send 10,000 rows to freeze the client | Arrays are bounded; an oversized list is rejected |
