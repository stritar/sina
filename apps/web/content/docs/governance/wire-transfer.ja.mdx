- 上限を超える電信送金でゲートが何を検出し、各検出結果がどの標準を引用するか
- 強制される承認ダイアログがどのように機能し、なぜ偽装できないか
- 監査証跡が各ステップで何を記録するか
</YouWillLearn>

これは SINA の主力フローであり、ドキュメントの残りの部分が指し示す正規のウォークスルーです。1
件の 60,000 ドルの電信送金を、リクエストから解決まで追っていきます。他のすべての統制されたフローは、これの変種です。

## リクエスト

AI は送金を提案します。送信するのはデータのみです。インテントと props であり、コンポーネントは決して送りません（[仕組み](/docs/how-it-works)を参照）。

```ts
{ intent: "wire_transfer",
  props: { amount: 6000000 /* $60,000 in cents */, currency: "USD", /* … */ } }
```

## 構造チェック

まず、厳格なパースです。すべてのフィールドがスキーマと照合されます。金額は最小単位の整数、通貨コードは実在し、口座識別子はチェックサムを通過します。スキーマが知らないフィールド、たとえば紛れ込んだ
`confirmButton` や余分な `cvv` があれば、ペイロード全体を拒否します。このリクエストは正しく整形されているので、次に進みます。

## ポリシーチェックが 3 つを検出する

形状は有効なので、ポリシーが実行されます。**3 件**の違反をトリガーし、それぞれがどこから来たかを引用します。

| 検出結果 | 深刻度 | 標準 |
|---|---|---|
| 報告対象取引（CTR） | `flag` | FinCEN, 31 CFR 1010.311 |
| 疑わしい活動のレビュー（SAR） | `flag` | FinCEN, 31 CFR Ch. X |
| 50,000 ドルの承認上限を超過 | `escalate` | SINA デュアルコントロールポリシー |

2 つの flag は情報提供です。記録されますが、ブロックはしません。作用するのは
**escalate** です。それは単純な確認を拒否し、`requiredComponent: "SecureWireDialog"`
を指定します。（深刻度は[エスカレーション](/docs/concepts/escalation)で扱います。）ここでも監査イベントが発火し、タイムスタンプ、ペイロード、3
件すべての違反、そして決定されたコンポーネントを伴います。何かがレンダリングされる前に、ブロックは記録に残ります。

<Callout variant="note" title="バンドは米ドルで定義されている">
  上記のすべてのバンドは `currency: "USD"` を前提としています。他の通貨での電信送金は構造チェックを通過し、バンドをスキップし、決定と監査証跡に
  `POLICY_BANDS_NOT_EVALUATED` フラグを伴います。そのため、この通過が黙って行われることは決してありません。独自の通貨にバンドを設定するには、カスタムルールをチェーンしてください。[ガバナンスルールを書く](/docs/governance/writing-a-rule)を参照してください。
</Callout>

## 強制されるダイアログ

SINA は確認ボタンの代わりに `SecureWireDialog` をマウントします。ダイアログは 2 人目の人物に次の手順を案内します。

1. 読み取り専用の要約で、正確な条件（金額、受取人）を**レビュー**する。
2. 承認者として**本人確認**する。ID と名前は発起人と異なっていなければならない。
3. 一度限りのコードで**確認**する。

送信すると、証拠は**サーバーに戻り**、憲章が再び実行されます。ダイアログ自体は何も検証しません。承認を収集するだけです。

<Callout variant="enforced" title="2 つのチェックが回避を不可能にする">
  2 回目のパスで、サーバーは敵対的なストリームが偽装できない 2
  つのことを強制します。**四つの目（フォーアイズ）**：承認者はサーバーが把握している発起人と異なっていなければならず、自分自身の電信送金を承認することはできません。**ペイロードバインディング**：承認は正確な条件に結び付けられ、サーバー上で再計算されるため、5,000
  ドルを承認して 60,000 ドルを実行することはできません。
</Callout>

下記のデモでは、発起人が自分自身の電信送金を承認しようとします。フォーアイズはそれを即座に拒否し、そこから先に進む方法はありません。

## ハッピーエンド

ガバナンスはエスカレーションします。単に拒否するだけではありません。*有効な*承認は
2 回目のパスでゲートを通過します。別のマネージャーが、正確な 60,000
ドルの条件に結び付けられます。送金はその後、完了した統制されたアクションとしてマウントされます。2
回目の[監査イベント](/docs/concepts/audit-trail)が、誰がどの条件で承認したか、そしてゲートが通過したことを記録します。一連の流れは後から再構成可能なままです。ブロック、承認、通過。

試してみてください。強制されるダイアログを開き、*別の*マネージャーとして承認すると、サーバーが再チェックし、決定が反転します。発起人として承認すると、拒否されます。

<Recap>
上限超過の電信送金 → 厳格なパースを通過 → 3 件の違反（2 つの flag、1 つの escalate） →
`SecureWireDialog` → *別の*承認者 + 一度限りのコード →
サーバーがフォーアイズとペイロードバインディングを再チェック →
承認されマウントされる、または拒否される。各決定に監査イベントが伴います。生の確認は決して選択肢になりません。
</Recap>
