SINA's golden rule is **never invent a limit**: every threshold, format, and required
field traces to a standard or a regulator, with the citation in the code. This page is
the receipt: every standard the Constitution encodes, and, for each, *what the code
actually checks*.

That last column is the point. A standards list is a compliance claim, and compliance
claims are exactly where a governance system starts lying to you. So each row says the
**mechanism**, not the aspiration: SINA computes an IBAN's mod-97 checksum for real, but
it does not screen an address against a sanctions list, and it does not perform a PCI
assessment. Where a rule is a thin stand-in for a deep obligation, the row says so.

Rules fall into three tiers, and the code keeps them apart:

- **Format**: checksums and code lists. Deterministic, so a payload satisfies them or it
  doesn't.
- **Regulatory**: real regulations. A `flag` records the finding in the
  [audit trail](/docs/concepts/audit-trail); an `escalate` forces a governed component; a
  `reject` refuses outright. Not yours to loosen casually.
- **SINA policy**: tunable product defaults (dual control, step-up limits). **Not law.**
  These are the ones you're expected to tune to your own risk appetite.

When the gate blocks a request, the `standard` from the matching row travels with the
violation into the audit record. A block is never a mystery, and an auditor can trace
it back to the line that made it. See [the contract](/docs/concepts/the-contract) for the
shape, and [write a rule](/docs/governance/writing-a-rule) to add one.

<Callout variant="enforced" title="This table is generated from the schemas">
  The catalog lives in the constitution package, not in this page, and a guard test binds
  the two: a rule citing a standard the catalog omits fails the build, and so does a
  catalog entry citing something no rule enforces. The docs cannot drift from the code,
  and cannot claim a check that doesn't exist.
</Callout>

## What the gate enforces, and where it stops

SINA is a render-time gate, so it acts on a request in five ways: it validates
structure and format, it escalates or flags on a threshold, it forces a disclosure to
be acknowledged, it requires a step-up or a second approver, and it redacts the audit
trail. Every row below is one of those five moves.

Three kinds of control sit outside that reach, on purpose. SINA does not screen a name
or address against a live sanctions or PEP list, it does not make a backend lending or
eligibility decision, and it does not hold a money-transmitter license. Each of those
needs a service and live data that a UI gate never sees. SINA runs **in front of** them,
it does not replace them, and a row that leans on one of them says so.

So the honest shape of coverage is this. The money-movement rails and the reporting
thresholds are here: Travel Rule, SAR, CTR, dual control, PCI field hygiene. Sanctions
screening, fair-lending decisions, and licensing stay out of scope and stay disclaimed,
never faked as a green check. A few gate-shaped rules are simply not built yet, such as
strong customer authentication for EU flows and open-banking data-access consent. To add
one, see [write a rule](/docs/governance/writing-a-rule).

<Callout variant="note" title="Out of scope is a feature, not a hole">
  A governance system earns trust by naming its edges. SINA sits in front of your
  screening and your backend decisioning, so the safe move is to state the boundary
  plainly rather than imply a check the code never runs.
</Callout>
