[工作原理](/docs/how-it-works)解释了 SINA *如何*做出决定。本节讲的是*内容*：如今
为 fintech 实际交付的规则，以及你为何可以信任它们。

章程分为两类规则，每个意图都属于其中之一：

- **受治理的**规则涵盖**操作**：转移资金、开设账户、发行卡片。它们携带策略（限额、
  审批、披露），并且可以升级到更严格的组件。
- **显示**规则涵盖**读取**：余额、交易、持仓。它们检查数据的*结构*（并对敏感字段进行
  脱敏），然后挂载一个展示型组件。它们从不升级。

存在哪些意图、每个意图挂载什么，其完整目录见
[受治理的组件与显示模式](/docs/governance/components-and-patterns)。

<BeforeAfter>
<Before title="基于提示词的规则">
“未经审批不得转移超过 $10,000”写在系统提示词里。它一直有效，直到模型犯糊涂、被越狱，
或者干脆就是错了。
</Before>
<After title="章程规则">
$10,000 的限额是一项 Zod 检查，会在每个请求上于服务器端运行。模型无法靠花言巧语绕过
一个解析器。
</After>
</BeforeAfter>

## 每个阈值都有出处

一个治理系统只有在其规则*站得住脚*时才值得信任。因此每条规则都带着它的出处。当关卡
拦截某项内容时，违规信息中会包含一个 `standard`，即它所依据的法规或策略，而该引用会
记入[审计记录](/docs/concepts/audit-trail)。拦截从来都不是一个谜。

代码将三类规则区分开来：**格式**标准（ISO 4217、IBAN、Luhn），源自真实金融监管的
**监管**阈值（FinCEN 的 CTR、SAR 和 Travel Rule 区间；FATF；Nacha），这些不该由你
随意放宽，以及**SINA 策略**默认值，你应当根据自己的风险偏好来调整（$50,000 的电汇
双重控制限额、各支付通道的授权上限）。

完整清单，以及 SINA 对每一项*究竟*检查什么，见
[标准与引用](/docs/governance/standards)。

## 威胁模型

SINA 假定产生意图的 AI 可能出错、被越狱，或怀有主动的敌意。设计上的问题从来不是
“模型会规矩吗？”，而是“当它不规矩时会怎样？”

| 攻击 | 它尝试做什么 | 为何失败 |
|---|---|---|
| **伪造控件** | 把一个 `confirmButton` 偷偷塞进 payload | 严格模式；未知字段在读取任何值之前就被拒绝 |
| **夹带卡片数据** | 包含一个 `cvv` 或完整的 PAN | 同样的严格解析；脱敏会在它进入日志之前将其掩盖 |
| **超限操作** | 一笔无审批的 $60,000 电汇 | 策略升级到第二审批人对话框；原始的确认无法挂载 |
| **自我审批** | 审批你自己的转账 | 四眼检查：审批人必须与服务器已知的发起人不同 |
| **偷梁换柱** | 审批 $5,000，然后执行 $60,000 | 审批被绑定到确切条款，并在服务器上重新计算 |
| **伪造数据** | 编造一个余额或一笔交易 | 对于读取，值由服务器提供；模型只挑选*要显示什么* |
| **数据外泄** | 返回一个未脱敏的账号 | 显示模式要求使用脱敏后的标识符 |
| **洪泛** | 发送 10,000 行以冻结客户端 | 数组是有界的 |

<Callout variant="enforced" title="这些并非假设">
  上面每一行都是 SINA 测试套件中的真实 payload。如果其中任何一个不再被拦截，构建就会
  失败，因此这些保证不会悄悄腐坏。
</Callout>

在一次真实请求中看看这些攻击中的若干个如何上演：
[$60k 电汇，端到端](/docs/governance/wire-transfer)。然后
[编写你自己的规则](/docs/governance/writing-a-rule)。
