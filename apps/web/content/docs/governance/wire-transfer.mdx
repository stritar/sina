This is SINA's flagship flow, and the canonical walkthrough the rest of the docs
point at. We'll follow a single $60,000 wire from request to resolution. Every
other governed flow is a variation on this one.

## The request

The AI proposes a transfer. It sends data only: an intent and props, never a
component (see [How it works](/docs/how-it-works)).

```ts
{ intent: "wire_transfer",
  props: { amount: 6000000 /* $60,000 in cents */, currency: "USD", /* … */ } }
```

## The structure check

First, the strict parse. Every field is checked against the schema: amount is an
integer in minor units, the currency code is real, the account identifiers pass
their checksums. Any field the schema doesn't know, like a smuggled
`confirmButton` or a stray `cvv`, rejects the whole payload. This request is
well-formed, so it moves on.

## The policy check finds three things

The shape is valid, so policy runs. It trips **three** violations, and each one
cites where it comes from:

| Finding | Severity | Standard |
|---|---|---|
| Reportable transaction (CTR) | `flag` | FinCEN, 31 CFR 1010.311 |
| Suspicious-activity review (SAR) | `flag` | FinCEN, 31 CFR Ch. X |
| Over the $50,000 approval limit | `escalate` | SINA dual-control policy |

The two flags are informational: recorded, not blocking. The **escalate** is the
one that acts. It refuses the plain confirm and names
`requiredComponent: "SecureWireDialog"`. (Severities are covered in
[Escalation](/docs/concepts/escalation).) An audit event fires here too, carrying
the timestamp, the payload, all three violations, and the decided component. The
block is on the record before anything renders.

<Callout variant="note" title="The bands are defined in USD">
  Every band above assumes `currency: "USD"`. A wire in another currency passes
  the structure check, skips the bands, and carries a
  `POLICY_BANDS_NOT_EVALUATED` flag in the decision and the audit trail, so the
  pass is never silent. To band your own currency, chain a custom rule: see
  [Write a governance rule](/docs/governance/writing-a-rule).
</Callout>

## The forced dialog

SINA mounts `SecureWireDialog` instead of a confirm button. The dialog walks a
second person through:

1. **Review** the exact terms (amount, recipient) in a read-only summary.
2. **Identify** as the approver, with an ID and name that must differ from the initiator.
3. **Confirm** with a one-time code.

When they submit, the evidence goes **back to the server** and the constitution
runs again. The dialog itself validates nothing. It only collects the approval.

<Callout variant="enforced" title="Two checks make it un-bypassable">
  On the second pass the server enforces two things a hostile stream can't fake.
  **Four-eyes**: the approver must differ from the server-known initiator, so you
  can't approve your own wire. **Payload binding**: the approval is tied to the
  exact terms, recomputed on the server, so you can't approve $5,000 and execute
  $60,000.
</Callout>

In the demo below, the initiator tries to approve their own wire. Four-eyes
refuses it outright, and there is no way to proceed from there.

## The happy ending

Governance escalates; it doesn't just refuse. A *valid* approval clears the gate
on the second pass: a different manager, bound to the exact $60,000 terms. The
transfer then mounts as a completed, governed action. A second
[audit event](/docs/concepts/audit-trail) records who approved, on what terms,
and that the gate passed. The whole story stays reconstructible later: block,
approval, pass.

Try it. Open the forced dialog and approve as a *different* manager, and the
server re-checks and the decision flips. Approve as the initiator and it refuses.

<Recap>
Over-limit wire → strict parse passes → three violations (two flags, one
escalate) → `SecureWireDialog` → a *different* approver + one-time code → server
re-checks four-eyes and payload binding → approved and mounted, or refused, with
an audit event at each decision. The raw confirm is never an option.
</Recap>
