SINA 中每一个由 AI 生成的界面都会经过相同的三个步骤：

1. **模型提出方案。** AI 发送一个<Term term="intent">意图</Term>：一个动词加上一些数据，
   比如带有金额和收款人的 `"wire_transfer"`。
   它从不指定组件。
2. **服务器做出决定。** 你的服务器让意图通过
   <Term term="constitution">章程</Term>，也就是你以 schema 形式编写的规则。
   它们回答一个问题：这是否被允许，如果允许，应该渲染什么？
3. **界面显示通过的内容。** SINA 挂载服务器所选择的组件。
   如果请求失败，任何不安全的内容都不会被渲染。

## 一切所依赖的那条规则

> **模型发送的是意图和 props，绝不是组件。校验只在服务器上运行。我们先校验，_然后_
> 才挂载。我们绝不先挂载再检查。**

为什么是你的服务器，而不是浏览器？因为**一旦 UI 到达屏幕，你就无法收回它。** React
会将它一片片地流式传输下来。不存在“取消渲染”。

所以检查必须在**任何东西挂载之前**运行。你能完全掌控的最后一处是你自己的**服务器**。
攻击者可以修改或跳过浏览器中运行的任何东西。那里的检查能拦住无心之失；**但它拦不住攻击**。

这就是回报。无论模型是出错、被越狱，还是充满恶意，都无关紧要：**它永远不决定渲染什么。**

## 一个意图长什么样

```ts
const intent = {
  intent: "wire_transfer",
  props: { amount: 6000000, currency: "USD", recipient: /* … */ },
};
```

注意*没有*出现的东西：没有按钮、没有对话框、没有布局。AI 描述的是它*想要什么*
（“把这笔钱转走”），从不描述它*应该长什么样*。

## 关卡检查什么

每个意图都会按顺序经过相同的四个步骤：

1. **结构。** payload 的形状是否完全正确？schema 是严格的，所以一个伪造的“确认”按钮
   或一个夹带进来的卡号就是一个*多余字段*，在读取任何值之前就被拒绝。
2. **策略。** 这些值是否遵守规则？金额是否在限额之内？是否需要第二位审批人？
   每个阈值都引用了一项真实的标准。
3. **决定。** 问题会变成*违规*，关卡随即决定：有效与否，以及如果需要更严格的组件，
   是哪一个。
4. **审计。** 每个决定都会发出一条记录，记录请求了什么、决定了什么，以及触发了哪些规则，
   敏感数据会先被脱敏。

一个决定总是以两种方式之一结束：**它挂载**（请求通过，SINA 挂载规则所选择的组件），
或**它被阻止**（不安全的版本从不挂载；它被直接拒绝，或被
<Term term="escalation">升级</Term>到更严格的组件，比如一个第二审批人对话框）。

<Callout variant="note" title="关卡会指定一个组件">
  关卡不会返回“允许 / 拒绝”。它会指定*某一个特定的*组件，形如
  `requiredComponent: "SecureWireDialog"`，或者拒绝。挂载的就是那个组件，别无其他。
  这是一套设计系统，而不仅仅是一个策略引擎。
</Callout>

## 三个层，一条流程

在底层，SINA 由三个层组成：token 与基础组件、治理接缝，以及领域章程。你大多数时候
只需考虑上面那条流程。这些层只是它的封装方式。

<Recap>
模型提出一个意图；服务器对照章程检查它；界面只挂载通过的内容。安全的请求变成真实的组件；
不安全的请求会被阻止，或被升级为一个受治理的组件。
