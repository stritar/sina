AI 可以读取你的风格指南然后无视它。但它无法无视一条在其请求与屏幕之间作为代码运行的
规则。这正是 SINA 带来的转变：规则不是 AI 参考的一份文档，而是它必须穿过的一道关卡。
AI 能*读取*的设计系统只是一条建议；它必须*穿过*的设计系统才是一种保证。精心编写的提示
词仍然可能被误读、遗忘，或被巧妙的输入所覆盖。而一条被强制执行的规则无法被说服让路。

## 智能体发送的内容

SINA 为模型提供一份意图动词的菜单，即一份清单：

```ts
[
  { intent: "wire_transfer", kind: "governed", summary: "Move money by wire" },
  { intent: "list_transactions", kind: "display", summary: "Show recent activity" },
  // …
]
```

模型选择一个动词并提供其 props。它描述的是一个目标，而不是在构建一个屏幕。

## 它永远无法做的两件事

- **它无法指定组件。** 清单里有的是动词，而非组件。SINA 在关卡运行*之后*才将动词映射到
  组件，因此模型并不知道那个原始的确认按钮存在。
- **它无法为读取操作编造数据。** 当模型请求*显示*余额或交易列表时，由你的服务器提供真实
  的值。模型选择*显示什么*，而绝不决定*那些数字是什么*。

把这两点放到 60,000 美元的电汇上：模型无法渲染确认按钮（它从未选择过组件），无法自行
批准这笔转账（批准需要*另一个*人，且在服务器端核验），也无法先批准一笔小额款项再替换成
一笔大额款项（批准与确切的条款绑定，而这些条款由服务器重新计算）。

<Callout variant="enforced" title="请求不等于执行">
  智能体可以*请求*任何东西。但它无法*执行*任何关卡未允许的操作。提议与渲染之间的那道
  鸿沟，正是 SINA 全部安全性所在之处。
</Callout>

## 试一试

这个演示运行的是**真实关卡**：与你的服务器会运行的代码相同，在服务器上运行，就在你按下
运行时。一个恶意的流试图夹带一个伪造的“确认”按钮；严格解析会在读取任何值之前就丢弃这个
多余的字段。切换请求，看看边界实际落在哪里。

## 你的智能体可以读取的文档

把一个编程助手指向这里，它就能直接使用这些文档：

| 资源 | 它是什么 |
|---|---|
| `/llms.txt` | 每一页的精选索引，供 LLM 抓取。 |
| 每页 `.md` | 每一页在 `/llms/docs/…` 下都有一个原始 Markdown 的孪生版本。 |

该索引以一段面向智能体的前言开头，秉承 SINA 自身的精神：将 UI 作为**意图**发出，即一个
动词加 props，绝不是一个伪造的组件；把它发送到服务器端的关卡；优先使用已注册的意图，
因为其他任何东西都会被拒绝。
