title: Brand & the locked boundary
description: Make SINA match your brand by overriding roles — but know which roles are off-limits, because a theme must never hide a safety signal.
---

Rebranding SINA is mostly a short list of role overrides. But not every token is
yours to change — and that boundary is itself a governance decision.

## Build a brand theme

Pick your brand color, its readable foreground, and any surface adjustments.
Everything else inherits.

```css
:root {
  --sina-color-primary: #6d28d9;
  --sina-color-primary-fg: #ffffff;
  --sina-color-primary--hover: #5b21b6;
  --sina-radius--md: 0.5rem;   /* softer corners, brand-wide */
}
```

Wrap it in a named scope (`[data-theme="acme"]`) if you support multiple brands, or
put it on `:root` for one. The typed `createTheme()` helper generates this and
checks your overrides at compile time.

## The locked boundary

Two kinds of token exist, and the theming API keeps them apart:

- **Brand-open** — surfaces, text, borders, `primary`, `secondary`, the success /
  warning / info roles, radius, spacing, type. These are yours. Rebrand freely.
- **Governance-locked** — `danger*`, the secure-surface tint, the focus ring, and
  the intent roles. The typed API **won't let you override these**.

<Callout variant="governance" title="Why lock anything?">
  A brand theme must never be able to make an error look calm, hide a focus ring
  from keyboard users, or disguise a secure-action affordance. Those aren't style —
  they're safety and accessibility signals. So the sanctioned path excludes them:
  `createTheme()` rejects a locked role at compile time.
</Callout>

<DoDont
  do={[
    "Override primary, surfaces, and radius to match your brand",

    "Re-check contrast after a heavy rebrand",
  ]}
  dont={[

    "Remove or dim the focus ring",

  ]}
/>

This is theming that can't accidentally break governance — the same principle as
the rest of SINA, applied to color.
