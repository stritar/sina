---
title: SINA を拡張する
sourceHash: 7dcc3685ebdf
---

SINA は 3 つの方向に成長します。`core` の新しいプリミティブ、`fintech` の隣に置く新しい統制されたドメイン、そして規則が成り立つことを証明する新しいテストです。以下の各レシピは、リポジトリのスキル（`/new-primitive`、`/new-schema`、`/adversarial-test`）に対応しています。

### core にプリミティブを追加する

`core` プリミティブはヘッドレスで、アクセシブルで、厳密にドメイン非依存です。境界は厳格です。`zod` なし、ドメインパッケージなし、ドメイン語彙なし（"$50,000" なし、"上限" なし、"承認" なし）、Tailwind なし。

1. **デザインの承認を確認する。** それが実装の前提条件です。承認された構造どおりに作り、UX を勝手に作り出さないでください。
2. **Radix の上に構築する。** `packages/core/src/<Name>/<Name>.tsx` に配置し、同じ場所に置いた `<Name>.module.css` でスタイルを当てます。フラットなクラス名、状態のための本物の擬似クラス、そしてセマンティック[トークン](/docs/theming/tokens)のエイリアスとなるコンポーネントごとの `--sina-<name>-*` トークン層です。生の色は決して書かないでください。
3. **アクセシビリティ基準を満たす。4 つすべて、譲れません。** サーフェスがフォーカスを閉じ込める箇所でのフォーカストラップ、正しい ARIA、完全なキーボード操作性、そして自動化された `axe`（jest-axe）のパスです。エラーと警告の状態は、対応する太字のステータスグリフをテキストの横にレンダリングし、色だけに頼ることは決してありません。
4. **テストとデモ。** `<Name>.test.tsx` に `expect(await axe(container)).toHaveNoViolations()` とキーボード/フォーカスのアサーションを加え、続いて playground のストーリーを作ります。

### 統制されたドメインを追加する

SINA は今日 1 つのドメイン `fintech` を同梱していますが、2 つ目は追加であって、書き直しではありません。共有される `@sina-design-system/governance` の継ぎ目が[契約](/docs/concepts/the-contract)、監査の発火点、そして `intercept` エンジンを所有し、電信送金については何も知りません。新しいドメインは、`fintech` と `fintech-react` を映した 2 つのパッケージです。

1. **純粋な Zod 憲章**（`packages/<domain>`、`governance` にのみ依存）。フォーマットのプリミティブ、引用された閾値（`// 31 CFR …`、決して捏造した数字ではなく）、`{ valid, violations, requiredComponent }` を返す規則、そして単一の評価エントリポイントを持つ 動詞 → 規則 のレジストリです。React なし、`core` なし、`theme` なし、UI なし。規則そのものを書くには、[ルールを書く](/docs/governance/writing-a-rule)に従ってください。
2. **`*-react` 層**（`packages/<domain>-react`）。`core` プリミティブをドメインのスキーマと組み合わせ、ゲートがすでに下した決定をレンダリングします。スキーマを書くことは決してなく、ペイロードを検証することも決してありません。ゲートはサーバー側にとどまります（[仕組み](/docs/how-it-works)を参照）。

契約が統一されているため、新しいドメインの規則は同じゲートに収まり、同じ監査イベントを発火し、同じ敵対的ハーネスで検証されます。ガバナンスはドメインごとに分岐しません。

### 敵対的テストを書く

規則はコンパイルできた時点では完成していません。敵対的なリクエストがそれを通り抜けられないときに、はじめて完成します。*有効な*リクエストが通ることをテストするのではなく、*無効な*リクエストが忍び込めないことをテストしてください。定番を網羅します。

- **密輸された項目**: 捏造された `confirmButton` や `cvv`。厳格なパースはそれを拒否しなければなりません。
- **上限を超えた値**: 閾値をわずかに超えたもの。正しいコンポーネントへエスカレーションしなければなりません。
- **バイパスの試み**: 少額で承認し、大額で実行する、あるいは自己承認する。サーバー側の束縛はそれを拒否しなければなりません。
- **洪水**: 過大な配列。その境界はそれを拒否しなければなりません。

何かが例外を投げたことだけでなく、決定そのものをアサートしてください。

```ts
const decision = evaluateFintechIntent(hostileEnvelope, ctx);

expect(decision.valid).toBe(false);
expect(decision.requiredComponent).toBe("SecureWireDialog"); // or null for a reject
expect(decision.violations.map((v) => v.code)).toContain("AMOUNT_REQUIRES_APPROVAL");
```

<Callout variant="enforced" title="必須チェックにする">
  これらのテストを必須チェックとして CI に組み込み、規則をひそかに弱める変更が、出荷される代わりにビルドを失敗させるようにします。
</Callout>
