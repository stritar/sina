---
title: Add a governed domain
description: The extensibility path the governance abstraction enables — a pure Zod constitution plus a react layer that composes it with core primitives
---

SINA ships one domain today — `fintech` — but the architecture was factored so a
second domain is additive, not a rewrite. The shared
`@sina-design-system/governance` seam is domain-agnostic on purpose: it owns the
interception contract, the audit emit point, and the `intercept` engine, and
knows nothing about wire transfers or any other vocabulary.

A new governed domain is therefore two packages that mirror `fintech` and
`fintech-react`.

## 1. A pure Zod constitution package

Create a `packages/<domain>` that depends on `governance` and **only**
`governance`. It contains:

- **Format primitives** — cited, reusable Zod schemas for the domain's data
  types, each tracing to a standard.
- **Cited thresholds** — the legible numeric limits, with the citation in the
  code (`// 31 CFR …`), never an invented number.
- **Rules** — each a `ConstitutionRule` returning the standard
  `{ valid, violations, requiredComponent }` contract via `intercept`.
- **A registry** — verb → rule + component, plus a single evaluate entry point
  (the way `fintech` exposes `evaluateFintechIntent`).

The boundary is hard: **no React, no `core`, no `theme`, no UI**. This package is
the constitution and nothing else.

## 2. A `*-react` layer

Create a `packages/<domain>-react` that composes a `core` primitive with a
`<domain>` schema and renders the decision the gate already made — exactly as
`fintech-react` does. It is the one package in the domain allowed to import both
`core` and the constitution.

It still **never authors schemas** (no `zod`) and **never validates** a payload.
A governed component collects intent, calls a server action that re-runs the
constitution, and renders the verdict — the gate stays server-side per
[The one invariant](/docs/concepts/the-one-invariant).

## Why this stays safe

Because the contract is uniform, the new domain's rules drop straight into the
same [interception gate](/docs/concepts/how-interception-works), emit the same
[audit event](/docs/concepts/the-audit-trail), and are exercised by the same
adversarial harness. Governance does not fork per domain — it is inherited from
`governance` and re-gated server-side everywhere.

To build the rules inside the domain, follow [Add a Schema](/docs/guides/add-a-schema);
for the components, mirror the governed-component recipe.
