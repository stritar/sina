SINA is a **design system with governance built in**, for applications where an
AI generates part of the interface.

It stops a model from rendering UI that breaks your **policy limits, 
your compliance rules, or your accessibility standards**.


You write those rules as code; the model sends an intent; your server 
validates it, and only then does a component render.



<FlowDiagram />

## The problem it solves

An AI asked to render a transfer confirmation will render one — including for
$60,000 that no one approved. The same gap produces dropdowns a screen reader
can't operate and views of data the user shouldn't have. The output looks
correct, which is why it ships.

A style guide can't prevent any of this, because nothing consults it at runtime.
SINA sits in the render path instead. The AI emits an
<Term term="intent">intent</Term> — a plain description of what it wants to show
— rather than a component. Your server validates that intent against the
<Term term="constitution">Constitution</Term>, your rules written as code, and
only then mounts something: the requested component if it passed, a stricter one
if it didn't, or nothing at all.

<Callout variant="governance" title="The rule">
  The model proposes; the server decides; the screen shows only what passed. SINA calls this **validate, then mount**.
</Callout>

## How it compares

| | What it is | Stops unsafe UI? |
|---|---|---|
| **A style guide / wiki** | Advice humans (and AIs) may ignore | No — advisory only |
| **A component library** (Radix, shadcn) | Great accessible parts | No — parts can still be misused |
| **SINA** | Accessible parts **+** a server-side check | **Yes — enforced by code** |

SINA isn't a competitor to a component library — it *includes* one (accessible
primitives on Radix) and adds the check on top.

## Who it's for

SINA is **free** (MIT), built for startups and individual builders who want a
governed design system without building the governance themselves. It ships
today for **fintech** — money movement, accounts, cards, disclosures — because
that's where getting it wrong is most expensive.

It's probably *not* for you if you don't generate UI with AI (though you can
still [use the primitives on their own](/docs/guides/adopt-incrementally)), or
if you can't run a check on a server — validation must happen server-side.
